Clasificación

Path Traversal (CWE-22 / CWE-626). Bypass de una validación de extensión de archivo mediante un byte nulo (%00).

MISSION_GOAL

Objetivo

Recuperar el contenido del archivo /etc/passwd del servidor, evadiendo una validación que exige que el nombre de archivo termine con una extensión permitida.

THEORY_CORE

Mecanismo de Bypass: El Byte Nulo (Poison Null Byte)

En este entorno, la aplicación espera un nombre de archivo (ej. filename=57.jpg). Como defensa, la aplicación implementa una validación que exige que la cadena termine con una extensión válida (como .jpg o .png).

El problema surge por la discrepancia en cómo se procesan las cadenas de texto en diferentes lenguajes o capas del sistema. Un byte nulo, inyectado como %00 en una URL, es interpretado por lenguajes y librerías basadas en C (bajo nivel) como un terminador de cadena, ignorando cualquier cosa que siga después de él.

Capa de la Aplicación Lectura de la Cadena Decisión
Alto Nivel (Validador PHP/Java) ../../../etc/passwd%00.png Aprueba el filtro porque la cadena entera, incluyendo lo que va después del %00, termina en ".png".
Bajo Nivel (Kernel / Sistema Archivos en C) ../../../etc/passwd.png Al leer el byte nulo (0x00), el Kernel considera que la cadena terminó ahí, descartando la extensión y abriendo el archivo objetivo.

El resultado es que la aplicación cree haber validado correctamente una imagen, mientras que el archivo realmente abierto es elegido por el atacante (CWE-626).

El navegador redirigió a la instancia única del laboratorio, con una URL aleatoria asociada a la sesión, mostrando la tienda "We Like To Shop" en estado "Not solved". De la barra de direcciones se copió dicha URL para reutilizarla en el navegador integrado de Burp.

Como primer intento se reemplazó el valor del parámetro por filename=/etc/passwd, sin ninguna extensión de archivo. El servidor respondió 400 Bad Request con el mensaje "No such file", confirmando que la validación de extensión rechaza este tipo de entrada de inmediato.

Como segundo intento se construyó el payload combinando una secuencia de traversal relativo con un byte nulo (%00) seguido de la extensión .png. Al enviar la petición, el servidor respondió 200 OK y el cuerpo de la respuesta contenía el texto plano de /etc/passwd.

Finalmente, se regresó a la pestaña del laboratorio en PortSwigger y se refrescó la página. La plataforma mostró el banner "Congratulations, you solved the lab!" y el estado cambió a "Solved".

PAYLOAD_BREAKDOWN

Análisis Estructural de los Payloads

Payload de control — 57.jpg

Nombre de archivo legítimo perteneciente al catálogo de productos, utilizado para confirmar el comportamiento normal del endpoint antes de cualquier intento de explotación.

Payload fallido — /etc/passwd

No contiene ninguna extensión reconocida por la validación (no termina en .jpg, .png ni similar), por lo que la aplicación rechaza la petición de inmediato con 400 Bad Request. Este intento confirmó la existencia del control de validación de extensión anunciado en el enunciado del laboratorio.

Payload exitoso — ../../../etc/passwd%00.png

La secuencia ../../../ al inicio realiza el recorrido de traversal habitual, retrocediendo tres niveles de directorio desde la carpeta base de imágenes hasta alcanzar la raíz del sistema de archivos.

El carácter %00 representa, una vez decodificado por el servidor, un byte nulo (0x00) insertado justo después del archivo objetivo y antes de la extensión.

La cadena .png colocada al final no tiene como propósito acceder realmente a un archivo con ese nombre; su único objetivo es hacer que la validación ("la cadena debe terminar en una extensión permitida") se cumpla a nivel de la aplicación.

Sin embargo, cuando el servidor utiliza esa misma cadena para abrir físicamente el archivo en el sistema operativo, la función subyacente de C interpreta el byte nulo como el final real de la cadena, y por lo tanto abre efectivamente ../../../etc/passwd, ignorando por completo la extensión falsa. El resultado es la lectura arbitraria de datos confidenciales.

SECURITY_PATCH

Mitigación recomendada

  • Rechazar explícitamente cualquier entrada que contenga bytes nulos (%00 o su equivalente decodificado 0x00) antes de realizar cualquier otra validación o de utilizar el valor para acceder al sistema de archivos.
  • Actualizar y mantener actualizado el entorno de ejecución (lenguaje, runtime y bibliotecas). La mayoría de los frameworks modernos bloquean automáticamente bytes nulos embebidos.
  • Validar la extensión del archivo únicamente después de canonicalizar la ruta completa (resolviendo secuencias de traversal y caracteres de control), y no sobre la cadena cruda recibida del cliente.
  • Sustituir el nombre de archivo controlado por el usuario por un identificador indirecto (un ID numérico de producto), de modo que el servidor construya la ruta real de forma aislada.
  • Adoptar un enfoque de lista blanca (whitelist) estricta sobre el nombre completo del archivo (por ejemplo, únicamente dígitos seguidos de una extensión permitida), en lugar de validar solamente el sufijo de la cadena recibida.
